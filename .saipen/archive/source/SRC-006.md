[P0] [CORE-001] saipenview/external_changes.py::ExternalChangeRegistry.recover_from_corrupt

EVIDENCE:
- `_load()` lines 200-209 treats a registry as degraded only when the canonical `external_changes.corrupt` marker exists; if neither marker nor primary persistence file exists, it explicitly sets `_load_corrupt = False`.
- `recover_from_corrupt()` lines 421-428 MOVES the canonical corrupt marker to a timestamped archive before attempting the replacement durable write.
- Lines 436-444 then clear `_load_corrupt`, call `_save()`, and on `_save()` failure restore only the in-memory `_load_corrupt = True`; the canonical marker is not restored.
- The method's own contract at lines 407-412 states that a failed commit leaves the degraded state and artifact as they were, but the implementation violates that contract.
- Existing regression `tests/test_src003_audit_clauses.py:204-209` verifies only that the SAME registry object remains degraded after `_save()` failure. Unlike the successful-recovery test at lines 192-195, it never instantiates a fresh registry after failure.
- Deterministic local reproduction with a corrupt temporary registry and `_save = lambda: False` produced:
  initial: degraded=True, marker=True, primary=False
  recover: ok=False, archived=<timestamped corrupt artifact>
  same process: degraded=True, marker=False, primary=False
  fresh registry after restart: degraded=False, pending=0, marker=False, primary=False

DEFECT:
Recovery is not failure-atomic. Once the marker has been renamed, a failed replacement write leaves no durable indication that the registry is untrusted. The current process remains fail-closed only because `_load_corrupt` survives in memory. After restart, `_load()` sees neither the canonical marker nor the primary registry and classifies the state as healthy and empty.

This defeats the collect safety invariant in `parser.py:1341-1346` and `parser.py:1632-1637`, both of which rely on `get_registry().is_degraded()` to refuse collection when external-change evidence cannot be trusted. A restart after this recovery failure can therefore turn unknown/corrupt boundary evidence into an apparently clean registry and permit a collect that no longer has proof that its boundary evidence is complete.

REPAIR:
- Make corrupt recovery transactional and crash/failure-safe.
- Do not remove the canonical corrupt marker before a replacement registry generation has been durably committed.
- Preferred sequence:
  1. While holding the registry lock, preserve the corrupt artifact to the timestamped archive by copy/evidence-preserving duplication rather than destructive rename.
  2. Keep the canonical corruption marker present.
  3. Durably write the replacement registry through a recovery-specific commit path that can operate while corruption is flagged.
  4. Only after the replacement write has succeeded atomically should the canonical marker be removed and `_load_corrupt` become false.
- If the replacement write fails, leave the marker intact and return failure.
- If final marker removal fails after the replacement write, remain degraded. A false negative is acceptable here; a false healthy state is not.
- Preserve any post-corruption PendingChange entries already accumulated in memory.
- Do not weaken the parser's fail-closed collect checks to work around this.
- Add restart/crash-window regression coverage, not merely same-object assertions.

VERIFY:
- Add a regression equivalent to:
  corrupt registry -> instantiate registry -> force replacement `_save` failure -> call recovery -> instantiate a NEW registry against the same persistence path -> assert `is_degraded() is True`.
- Assert the canonical marker or an equivalent durable untrusted-state indicator remains discoverable after failed recovery.
- Assert the corrupt evidence archive is retained.
- Assert successful recovery still survives restart and retains post-corruption pending entries.
- Assert a marker-removal failure also remains fail-closed across restart.
- Re-run the complete `TestCorruptRegistryRecovery` group and collect-boundary tests on Windows.
- Required invariant: no interruption or failure point in recovery may transition a subsequent process from UNKNOWN/CORRUPT evidence to HEALTHY/EMPTY evidence without a completed durable replacement commit.

[P1] [W2-001] saipenview/runtime.py::ProcessManager.launch / ProcessManager.stop_all; saipenview/api.py::Api.stop

EVIDENCE:
- `ProcessManager.launch()` reserves agent ownership at runtime.py:544 before expensive launch preparation begins.
- The reserved launch does not enter `_processes` until runtime.py:622-623, after `engine.build_command()`, environment preparation, `subprocess.Popen()`, Job Object assignment, `AgentProcess` construction, and session creation.
- `ProcessManager.stop_all()` at runtime.py:1241-1249 snapshots ONLY `_processes` entries whose status is `"running"`. It does not close launch admission, inspect ownership reservations, wait for in-flight launches, or establish a shutdown generation/barrier.
- `Api.stop()` at api.py:2887-2902 calls `_process_manager.stop_all()` as its agent-shutdown mechanism. `Api.start()`/`stop()` contain no ProcessManager launch-admission state.
- `RootOwnership.agent_owns()` deliberately treats a reservation as "live or launching", but `stop_all()` does not use that authoritative launching state.
- Deterministic reproduction:
  1. A test engine's `build_command()` blocked after `reserve_agent()` succeeded.
  2. `pm.is_running(root)` returned True because ownership was reserved.
  3. `pm.list_running()` contained zero processes because launch had not reached `_processes`.
  4. `pm.stop_all()` returned.
  5. The blocked build was released.
  6. `launch()` returned `{"ok": True, ...}` and spawned PID 4038.
  7. `pm.is_running(root)` was True AFTER `stop_all()` had completed; `get_status()` reported the agent as `"running"`.
  8. The audit explicitly killed the reproduced child afterward; ownership then returned False.
- Existing `tests/test_lifecycle.py::TestConcurrentLaunch` proves two launches for one root are serialized, but repository search found no launch-vs-stop_all or shutdown-vs-in-flight-launch regression.
- The service uses `ThreadingHTTPServer`, and `_dispatch()` invokes the selected Api callable outside the service lifecycle lock. An already-running RPC can therefore be inside `launch_agent()` while another thread performs service/API shutdown; stopping the listener does not retroactively cancel a backend call already executing.

DEFECT:
`stop_all()` is a snapshot operation, not a lifecycle barrier. A launch that has already reserved ownership but has not yet published its `AgentProcess` is invisible to shutdown. Shutdown can therefore report completion and proceed to stop scanners/watchers/registry infrastructure, after which the in-flight launch finishes and leaves a live Core agent in a backend that has already been stopped.

This violates the shutdown invariant that no SAIPENVIEW-owned agent survives `Api.stop()`. It also creates state drift: the agent continues mutating its project while the owning viewer/service has stopped normal observation and lifecycle management.

The race is not theoretical timing noise; the launch window includes arbitrary `engine.build_command()` work and process creation, and was deterministically reproduced.

REPAIR:
- Introduce an explicit ProcessManager launch-admission/lifecycle gate shared by `launch()` and shutdown.
- `stop_all()` must atomically close admission BEFORE it determines what must be terminated.
- A launch already in progress must satisfy exactly one of two outcomes:
  1. it becomes fully registered before the shutdown snapshot/barrier and is then terminated by that shutdown, or
  2. it observes the closed admission/generation, rolls back its reservation/process/session as applicable, and returns a controlled shutdown/cancel result.
- Do not rely on `_processes` alone to represent launch-in-progress state; the ownership reservation intentionally exists before `_processes`.
- A robust implementation may use a lifecycle gate + generation or an in-flight-launch counter/Condition. The critical invariant is that check/admit -> spawn/register cannot cross the shutdown barrier unseen.
- If process creation already occurred when shutdown wins, prove death before releasing ownership, preserving the existing fail-closed stuck-agent behavior.
- Because `Api` is deliberately restartable, `Api.start()` must explicitly reopen ProcessManager launch admission for the new lifecycle generation. Do not make `stop_all()` permanently disable the manager.
- Prefer also rejecting new service RPC dispatch once service state is `"stopping"`; this narrows the race but does NOT replace the ProcessManager barrier because an RPC may already be executing.
- Preserve current one-agent-per-root semantics and the shared RootOwnership single-writer invariant.

VERIFY:
- Add a deterministic regression using a blocking engine:
  1. launch thread reserves root and blocks before `_processes` insertion;
  2. call `Api.stop()` or `ProcessManager.stop_all()`;
  3. release the launch;
  4. assert no live process remains, ownership is eventually released only after proven death/no-spawn, and launch reports controlled cancellation/refusal rather than success.
- Add the complementary ordering: allow launch to become registered immediately before shutdown acquires its barrier; assert shutdown sees and kills it.
- Add restart coverage: stop -> start -> a fresh launch succeeds normally.
- Add service integration coverage with one in-flight `launch_agent` RPC while `SaipenViewService.stop()` executes; after stop returns there must be zero live/launching agents.
- Re-run existing concurrent-launch, kill, session, ownership and lifecycle suites.

REPAIR: Preserve the existing list-based callback compatibility but extend BackgroundScanner._do_scan to forward `completed_roots=result.completed_roots` and `unresolved_roots=result.unresolved_roots`; extend Api._set_cache with optional provenance kwargs and use them exactly as it currently uses provenance extracted from a ScanOutcome. [P1] [CORE-006] saipenview/external_changes.py::ExternalChangeRegistry durability recovery
EVIDENCE: A failed record/acknowledge sets `_degraded=True`. Successful later record or acknowledge operations do not clear it, and flush assigns `self._degraded = self._degraded or not ok`, making the state sticky. is_degraded documents the condition as including when "the last persistence write failed". Focused reproduction forced the first `_save` to fail: record returned -1 and degraded became true. A second record then performed a real successful atomic save containing both in-memory entries, but the same registry remained degraded=true. Constructing a fresh registry from that now-valid file immediately loaded both entries and reported degraded=false. parser.collect_outbox_entry and its commit-time freshness precheck both fail closed whenever is_degraded() is true, so the running process continues refusing collect despite its complete registry snapshot now being durably valid.
DEFECT: One boolean conflates two different trust failures: corrupt/unreadable state loaded from disk, where unknown evidence may have been lost and fail-closed must remain sticky, and a transient write failure where the complete in-memory registry can later be durably rewritten. Because the transient condition has no recovery transition, a temporary filesystem failure can disable collect for the rest of the process lifetime even after persistence has fully recovered.
REPAIR: Track load-corruption/untrusted-state separately from transient write-durability failure. A successful full snapshot save may clear the transient write-failure state because it durably writes the entire current in-memory registry, but it must NOT silently clear a corrupt-load condition where unknown prior evidence may have existed. Keep collect fail-closed while either unresolved trust condition remains and provide only an evidence-safe recovery path for corrupt-load state.
VERIFY: Force one record save failure, then allow a later full registry save to succeed; assert the persisted snapshot contains every in-memory pending entry, transient degraded state clears, and collect is no longer blocked solely by that recovered failure. Separately start from malformed/corrupt persisted JSON, perform ordinary records/saves, and prove the corrupt-load trust failure remains fail-closed until an explicit reconciliation/reload recovery proves the boundary safe.
